# 设计决策记录（ADR）

只记录**不这样选就会出问题**的决定，以及已经实测验证过的边界。
每条都尽量附上可复现的证据，避免以后有人（包括我自己）凭直觉把它改回去。

---

## ADR-001 用 `-c copy` 把新音频封进 MKV，而不是重新压制

**决定**：源视频第 1 条视频流 + 新音频第 1 条音频流，`-c copy` 直接封进 MKV。

**证据**（`SwapIntegrationTests.两个流都必须逐字节不变地拷进输出`）：
源视频流 SHA256 与输出内视频流 SHA256 完全一致，音频流同样一致。

```
源视频流   SHA256=7c2159609c734687ce8bb9d7d6fd292377f70fd497fffc0aa566ec1bd3529414
输出视频流 SHA256=7c2159609c734687ce8bb9d7d6fd292377f70fd497fffc0aa566ec1bd3529414
源音频流   SHA256=ed60058e795d9233e6340c1c909b5eb60fee7f7b73eca603449ce7503d9bb31c
输出音频流 SHA256=ed60058e795d9233e6340c1c909b5eb60fee7f7b73eca603449ce7503d9bb31c
```

**代价**：音频必须是线性 PCM，体积比源视频里的 AAC 大 10~20 倍。用户必须知道这一点，
所以在选框里明确显示"全程未重编码"和预估体积。

## ADR-002 `-avoid_negative_ts disabled` 是强制项

**决定**：正式输出的命令里永远带 `-avoid_negative_ts disabled`。

**为什么**：负偏移（音频提前）会让音轨时间戳变成负数。MKV 容器默认行为是把负数"修正"掉，
但修正方式是**把视频整体往后推**，而不是裁掉音频开头。结果：用户填 `-300`，
画面整体推迟 0.3 秒，和源视频时间轴对不上，**而且不报任何错**。

**实测数据**（`-itsoffset -0.3` 封进 MKV，ffmpeg n8.0）：

| 参数 | 视频 start | 音频 start | 结论 |
|:--|:--|:--|:--|
| 默认 | `0.300` | `0.000` | ⛔ 静默错误 |
| `disabled` | `0.000` | `-0.300` | ✅ 正确 |

**已验证 `disabled` 不会产生坏文件**：`ffmpeg -f null -` 完整解码该文件 exit=0。

**守护测试**：`CommandBuilderTests.负偏移_必须关闭avoid_negative_ts`、
`SwapIntegrationTests.负偏移_音频提前且视频起点保持不动`。

## ADR-003 `-itsoffset` 的位置是有语义的

**决定**：偏移参数插在**音频输入的 `-i` 之前**，且视频输入之前绝不插入。

**为什么**：`-itsoffset` 只作用于紧跟其后的那一个输入。位置错了不报错，只是偏移静默失效；
如果误插在视频前，会把画面整体推走 —— 正好是 ADR-002 要防的那个后果。

**开发过程中真的写错过一次**（把 `-itsoffset` 加在视频 `-i` 之前），
被 `CommandBuilderTests.偏移参数必须紧跟在音频输入之前` 当场逮住。

## ADR-004 只有"物理上不可能"才拦住用户

**决定**：开始按钮变灰的条件只有两个 —— 槽位为空，或文件里没有视频流 / 没有线性 PCM 流。
时长不一致、体积过大、8 位位深、浮点 PCM、CAF 容器、多音轨，**全部只出提醒**。

**为什么**：目标用户是音频制作者。他们最怕的不是报错，而是程序悄悄替他们做判断；
反过来，因为"时长差 0.2 秒"就不让干活同样不可接受（视频和音频天然有帧对齐误差）。

**推论**：界面上不该有"验证通过/不通过"这种审判式状态，只平铺事实 + 在有风险处标琥珀色。

## ADR-005 位深不能用 `sample_fmt` 推断

**决定**：位深取 `bits_per_sample`，回退 `bits_per_raw_sample`。

**为什么**：实测 `pcm_s24le` 的 `sample_fmt` 是 **`s32`**。
按 `sample_fmt` 判断会把 24 位显示成 32 位，直接误导用户对自己 DAW 导出设置的判断。

**守护测试**：`SlotEvaluatorTests.位深取bits_per_sample而不是sample_fmt`。

## ADR-006 时长比对容差 0.1 / 0.5 秒

**决定**：`≤ 0.1 秒` 视为一致（不显示差异）；`0.1~0.5 秒` 显示"基本一致"（灰字）；`> 0.5 秒` 才出琥珀提醒。

**为什么**：MKV/MP4 的视频和音频流时长几乎不会严格相等，差一帧（约 33 ms）是常态。
不容差就会满屏黄字，用户很快就学会无视告警 —— 那还不如不报。

## ADR-007 输出先写 `.partial.mkv` 再改名

**决定**：ffmpeg 输出到 `<名字>.partial.mkv`，成功后 `File.Move` 到最终名。

**为什么**：中途失败或用户取消时，绝不留下一个看起来能用、实际是半截的 MKV。
`.partial` 必须插在扩展名**前面**，因为 ffmpeg 靠扩展名推断容器。

**附带决定**：命令里用 `-n` 而不是 `-y`。输出名由程序保证唯一，所以正常情况永远不冲突；
万一冲突，`-n` 让 ffmpeg 直接失败退出，而不是弹一个看不见的交互提问把进程挂死。

## ADR-008 丢弃全部容器元数据

**决定**：`-map_metadata -1`，不复制标题、艺人、creation_time 等。

**为什么**：源容器的 `duration` 标签是按**旧音轨**写的，复制到新文件可能和新音轨的实际时长冲突，
某些播放器会据此显示错误的进度条。宁可少带信息，不要带错信息。

**已知取舍**：封面、章节、字幕也一并丢失。用户的需求原话是"其他全部丢弃"，且这类源文件
（平台下载的 MV）基本没有需要保留的元数据。如果以后有人需要，应该做成显式选项而不是默认行为。

## ADR-009 用 ffprobe 而不是 `ffmpeg -i` 取流信息

**决定**：额外打包 `ffprobe.exe`，用 `-print_format json` 取结构化信息。

**为什么**：`ffmpeg -i` 的输出是给人看的文本，格式随版本变化，解析它容易在升级 ffmpeg 后静默出错。
代价只有几 MB。

## ADR-010 构建脚本分 `.bat` + `.ps1` 两层，`.bat` 保持纯 ASCII

**决定**：逻辑全在 `build.ps1`（UTF-8 带 BOM），`build.bat` 只做纯 ASCII 转发。

**为什么**（实测踩过）：
- `cmd.exe` 逐字节读 `.bat`，按 ANSI 代码页解释。**GBK 下某些汉字的尾字节是 `0x5C`（反斜杠）**，
  会被当成续行符，脚本从那里开始整体错位 —— 表现为一堆毫不相关的 `'not' is not recognized`。
- Windows PowerShell 5.1 在 `.ps1` 没有 BOM 时按 ANSI 读取，中文变乱码。

**验证方式**：`[IO.File]::ReadAllBytes('build.bat')` 的最大字节值应 ≤ 127。

## ADR-011 绿色目录而不是单文件 exe

**决定**：`PublishSingleFile=false` + `SelfContained=true`，发布成目录。

**为什么**：单文件 exe 每次启动要把自己解压到临时目录，冷启动慢；
而且用户无法替换 `bin\ffmpeg.exe`（音频制作者迟早想换新版或换带硬件编码的构建）。

**代价**：根层 200+ 个文件，非技术用户会困惑。缓解方式是在使用说明里明确"只管双击 exe，不要删 bin"。
这是目前已知最难看的一处权衡。

## ADR-012 主界面只承载核心动作，其余全部收进弹窗

**决定**：主界面 = 左右两个文件卡片 + 通栏「开始」按钮 + 时长条（内含偏移入口）+ 右上角「设置」。
偏移设置独立成窗；保存位置 / 环境检查 / 关于收进「设置」；完成结果用弹窗。

**为什么**：初版一屏里同时有 选择/更换/时长/偏移/预览/开始/保存位置/完成/环境检查 九件事，
用户在截图里第一眼看到的是"不知道先看哪"。低频功能和"只在完成后才需要"的信息都不该占主界面。

**代价**：偏移和保存位置多了一次点击。判断值得，因为它们是低频动作，
而"两个框 + 一个开始"是每次都要走的路径。

## ADR-013 同一条信息只在一个地方出现

**决定**：固定分工 —— 卡片只显示文件名/规格/补充信息，时长条只给时长结论，
提醒区只给后果与建议（不重复差值）。

**为什么**：初版把源音轨信息在视频卡里写了两遍；采样率不一致在音频卡、时长条、提醒区各写一遍。
信息重复不只是不美观，它会让用户怀疑"这两处是不是在说不同的事"。

**具体取舍**：
- 源音轨由卡片的补充行承担，`SlotEvaluator.EvaluateVideo` 就**不再**生成这条 Note。
  只有"丢掉的比显示的多"（多音轨）才额外提醒。有测试锁住"不重复"。
- 时长差只在时长条给一次，提醒区只说后果（"成品结尾会静音 0:05"）。

## ADR-014 状态行没有内容时不占位

**决定**：`ShowStatusArea = Busy || 状态行非空`。两个文件就绪时返回空字符串，整行塌缩。

**为什么**：曾写成"可以开始了。全程不重编码……"常驻在主按钮下方。
但按钮已经是通栏高亮主色，"开始"二字含义自明，下面再挂一句是纯粹的视觉噪音。
用户明确指出这一点，判断正确。

**推论**：也不为"有提醒"这一情况写提示 —— 提醒自己就在上面一行且带「详情」链接，
再说一遍就是同一句话说两遍。

## ADR-015 卡片内容垂直居中，而不是用信息去填满

**决定**：卡片内容 `VerticalAlignment="Center"`。

**背景**：卡片有 `MinHeight="190"` 且会被星号行拉伸，内容通常比卡片矮。
初版是顶端对齐 → 卡片上半有内容、下半一片死白，用户反馈"信息框内太空了"。

**试过的两条路**：
1. 加信息去填（补了帧率、像素格式、Profile、声道布局、`sample_fmt`、码率、磁盘体积）——
   信息确实更有用了，但**治标**：内容越多，用户越需要它好读，而空白只是被稀释。
2. 内容居中 —— **治本**：空白被均分到上下，视觉自然平衡，也不再需要为了填空而堆信息。

两者都保留了：信息补充本身有独立价值（核对 DAW 导出、排查拷贝失败），
但**居中才是解决"空"的那个决定**。

**顺带的收益**：空状态本来就是居中的，改完之后"没选文件"和"选好文件"两种状态行为一致。

**踩过的坑**：改完之后窗口底部的富余留白还在（内容底 519，窗口 559），
又收了一次高度到 506。这个数字是量出来的，不是估的。

## ADR-016 文字对比度以 WCAG AA（4.5:1）为硬下限

**决定**：界面上所有会显示的文字，对比度必须 ≥ 4.5:1。三档文字色为
`#2E2923`（11.0:1）/ `#6F6659`（5.3:1）/ `#7A7164`（4.9:1），均相对页面底 `#F5F1E8` 计算。

**为什么**：用户直接反馈"设置里的字和背景对比度不明显，看着很累"。
实测初版：次要文字 `#8C8375` = 3.4:1，最浅提示 `#A79E8E` = 2.4:1，**都不达标**。

**为什么这条要写成 ADR**：米黄色系天生偏浅，很容易顺着"再柔一点"的直觉把文字调浅。
那样确实更"柔和"，但代价是读不清。**柔和应该体现在背景和描边，不能体现在文字上。**

**推论**：`Palette.cs` 里每个色值旁边都标了对比度，改色必须重新核对。

## ADR-017 偏移：入口整块可点，输入同时给毫秒和秒，并在时长不一致时主动引导

**三个决定，都来自用户反馈**：

1. **入口整块可点**。初版时长条右侧只有"无"两个字是链接，命中区极小。
   现在"音频偏移 + 值 + ›"是一个整体按钮，设过偏移后变浅绿底（`Classes.active` 绑定 `HasOffset`）。
2. **同时显示秒**。输入毫秒时旁边实时显示 `= -0.3 秒`。
   理由：用户在 DAW 里量到的偏差是"0.3 秒"量级，只给毫秒要在脑子里除 1000。
3. **时长不一致时主动引导**。时长条中间出现
   "如果只是整体差了一点，可以用右侧「音频偏移」校正"。
   理由：偏移是低频功能，用户看到"音频短 0:05"时未必知道旁边那个入口正是为这种情况准备的。
   只在差值超容差时出现，正常不占位。

## ADR-018 提醒不用行内展开，改成独立弹窗

**决定**：主界面只在时长条下方显示一行提醒摘要 + 一个「详情」按钮，完整清单在
`NoticesDialog` 弹窗里。**不做行内展开。**

**为什么**（这是用户实际报的 bug）：初版把提醒做成行内可展开区。展开后内容变高，
把「开始」按钮和状态行**推出了窗口下边界** —— 用户看到按钮变成了「收起 ∧」，
但展开的内容一个字都看不到，于是报告"点详情没反应"。

**根因**：主界面是固定高度的窗口，任何"点击后内容变高"的交互都会挤坏布局。
弹窗让主窗口高度恒定，从根上不存在这个问题，也和偏移/设置的做法一致。

**顺带的收益**：所有提醒（视频文件、音频文件、两者之间、体积）集中成一份带来源标注的清单，
比散在两个卡片里更容易看清全貌。卡片里不再挂 `ItemsControl`。

## ADR-019 界面尺寸反复出错的教训

这一轮的布局改动来回折腾了很多次，记录一下错在哪，避免以后再犯。

**症状**：底部「开始」按钮和状态提示反复被裁掉；期间还出现过"内容太松"（用户说"太空"）
和"内容太挤"两个相反方向的抱怨。

**我犯的三个错**：

1. **反复靠"估算窗口高度"来避免裁切。** 每次内容一变（加了提醒行、提示移到别处）
   就要重新猜一个数字，猜错就裁切。先后试过 560 / 604 / 644 / 648 / 672 / 680，都没有稳定性。
   → 正确做法是让布局自己适应（星号行伸缩），窗口高度取一个有余量的固定值。

2. **用 `SizeToContent="Height"` 兜底，但它在内容动态变化后不重新测量。**
   实测：三个不同状态的窗口高度都是 478 —— 都是启动那一刻（空状态）测出来的，
   于是填充状态全被裁掉。

3. **量错指标。** 我用 `Content.DesiredSize` 判断"内容放得下"，它报 408 < 560 看起来没问题，
   但截图显示明显裁切 —— 因为 `DesiredSize` 是在**约束下**测量的，会返回约束后的值。
   `SizeToContent` 也栽在同一个坑上。
   → 可靠的验证方式是**截图对照**，不是读 `DesiredSize`。

**留下的一条可复用经验**：主界面要预留"提醒区"的高度（`MinHeight`），
否则卡片所在的星号行会把下面的元素挤出窗口。

## 待确认 / 未验证

- **负偏移的成品在剪辑软件里的行为**：已验证 mkv 能正常解码、播放器能播，
  但"NLE 时间线是否正确对齐"需要在真实剪辑软件里确认。预览功能（走相同的偏移参数）
  是给用户自查用的退路。
- **`-progress pipe:1` 的 `out_time_us` 在非 mkv 输出上的精度**：目前只用于百分比显示，
  即使偏一点也只影响进度条观感，不影响产物。
