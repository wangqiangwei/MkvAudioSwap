## 一、这个工程是什么

给翻唱作者用的 Windows 桌面小工具：**把 MV 的画面原样保留、换成你自己的音频。**

**核心原理是一条 ffmpeg 命令：**

```
ffmpeg -i 视频 -i 音频 \
       -map 0:v:0 -map 1:a:0 \
       -c copy \
       -avoid_negative_ts disabled \
       -n -f matroska 输出.mkv
```

`-c copy` 是"不编码、直接搬"。所以视频流和音频流都是**逐字节拷贝**的，画质音质零损失。

**这个工具的价值不在于"会写这条命令"，而在于"让你不用写、也不会写错"。** 具体见第五节。

### 目录位置

```
<仓库>\                      ← 仓库
<仓库上一级>\测试素材\        ← 手工测试素材（生成物，不在仓库里）
```

## 二、技术选型

| 项 | 选择 | 说明 |
|:--|:--|:--|
| 运行时 | **.NET 9** | 用户已有 SDK 9.0.315 |
| 界面 | **Avalonia 12.0.5** | 用户正在用同一套框架重构另一个项目 |
| 发布 | `PublishSingleFile=false` + `SelfContained=true` | 绿色目录，见第七节 |
| 目标平台 | Windows x64 | 只支持这一个 |
| 外部依赖 | ffmpeg / ffprobe | 打包在 `bin\`，不需要用户安装 |

**为什么用绿色目录而不是单文件 exe：** 单文件 exe 每次启动要解压自己到临时目录（冷启动慢），
而且用户无法替换 `bin\ffmpeg.exe`。音频制作者迟早会想换成自己带的 ffmpeg build。
代价是根层有 200 多个文件，使用说明里已注明"只管双击 exe，不要删 bin"。

## 四、实测出来的 ffmpeg 行为（全部有数据）

这一节是**最该先读的部分**。下面每一条都是实际跑出来的，不是从文档抄的。

### 4.1 不写 `-c copy`，ffmpeg 会悄悄重新编码音频

同一支视频配同一个无损音频：

| 写法 | 输出音频编码 | 体积 |
|:--|:--|:--|
| `-c copy` | pcm_s24le（无损） | **8.49 MB** |
| 不写 `-c copy` | vorbis（有损） | 0.46 MB |

差 18 倍。**画面看起来完全正常，不报任何错。** 这是"看起来成功但结果是错的"的典型。
（顺带：这也给了用户一个自查手段 —— 体积突然很小就是被压过了。）

### 4.2 负偏移会悄悄推迟画面（不报错）

`-itsoffset -3`（音频提前 3 秒），ffmpeg 的默认行为不是裁掉音频开头，
而是把**整个画面往后推 3 秒**：

| 参数 | 视频起点 | 音频起点 |
|:--|:--|:--|
| 默认 | **3.000 秒** | 0.000 |
| `-avoid_negative_ts disabled` | 0.000 | **-3.000 秒** |

所以命令里**必须**带 `-avoid_negative_ts disabled`。删掉不会报错，只会让用户的画面整体错位。

（小数会随时长估算出现 -2.952 / -3.000 之类的差异，要紧的是画面起点有没有被推后。）

### 4.3 `-itsoffset` 只作用于紧跟其后的那个输入

位置写错了**不报错**，只是参数被无视 —— 用户以为设了偏移，实际是 0。
所以参数必须紧贴在音频的 `-i` 之前。`CommandBuilderTests.偏移参数必须紧跟在音频输入之前` 守着它。

### 4.4 哪些音频编码能 `-c copy` 进 MKV

实测（ffmpeg n8.0，5 秒立体声 48 kHz，逐个封进 matroska 并回读）：

| 编码 | 结果 | 回读 | 性质 |
|:--|:--|:--|:--|
| pcm_s16le / s24le / s32le / f32le | ✓ | 同名编码 | 无损（未压缩） |
| **flac** | ✓ | flac | **无损（压缩）** |
| **alac** | ✓ | alac | **无损（压缩）** |
| **wavpack** | ✓ | wavpack | **无损（压缩）** |
| mp3 | ✓ | mp3 | 有损 |
| aac | ✓ | aac | 有损 |
| opus | ✓ | opus | 有损 |
| vorbis | ✓ | vorbis | 有损 |
| ac3 | ✓ | ac3 | 有损 |
| **truehd** | **✗** | — | `sample rate not set` → `Could not write header` |

**关键区分**（早先的实现把两件事混成了一个判据，见 6.1）：

- "能不能不重编码地搬进 MKV" → 决定技术上做不做得成
- "编码本身有没有压缩" → 决定成品有没有损失

MP3 能 copy 但本身有损；FLAC 能 copy 且仍然无损。

### 4.5 位深不能用 `sample_fmt` 推断

实测 `pcm_s24le` 的 `sample_fmt` 是 **`s32`**（24 位打包在 32 位容器里）。
按 `sample_fmt` 判断会把 24 位显示成 32 位，直接误导用户核对 DAW 导出设置。
必须读 `bits_per_sample`，回退 `bits_per_raw_sample`。

### 4.6 mp4 容器能装 PCM

实测 `-c copy` 把 pcm_s24le 装进 mp4，**exit 0、成功**。
所以"MP4 装不了 PCM"是错的。真正的风险在**播放器和平台兼容性参差**，
以及"输出格式固定"是为了少一类出错的可能。早期文档写错过这一点。

### 4.7 未压缩 PCM 的体积（用真实文件校准）

48 kHz / 24 位 / 立体声 = **0.275 MB/秒**（实测：30 秒的 CAF = 8.24 MB）

| 时长 | 体积 |
|:--|:--|
| 3 分钟 | 约 49 MB |
| 5 分钟 | 约 82 MB |
| 10 分钟 | 约 165 MB |

同长度 AAC 128 kbps 约 4.6 MB —— 差约 18 倍。
早期文档写过"5 分钟约 1.7 GB"，**算错了 20 倍**。

### 4.8 mp4 存不了负时间戳：预览的负偏移会被静默吃掉（用户报的 bug）

**症状**："音频偏移对生成的预览视频不生效，那这个预览功能就没有意义了。"

正式输出是 mkv，负偏移靠 `-itsoffset` + `-avoid_negative_ts disabled`（4.2），没问题。
但**预览是 mp4**，而 mp4 根本存不了负时间戳：mov 复用器会无视
`-avoid_negative_ts disabled`，自己把负的部分处理掉，**不报任何错**。

实测（ffmpeg n8.0，30 秒素材，`-t 10`，`ffprobe` 回读预览）：

| 偏移 | 预览的音频时长 | 音频首个包 pts | 用户感受 |
|:--|:--|:--|:--|
| `0` | 10.00 秒 | -0.021 | 正常 |
| `-0.3` | 9.70 秒 | -0.321 | 结尾少 0.3 秒，几乎看不出 |
| `-3` | **7.00 秒** | -1.016 | 结尾 3 秒没声音 |
| `-8` | **2.00 秒** | -1.011 | 基本没声音 |
| `≥ -10` | **没有音频** | — | 预览是哑的 |

规律是 `音频时长 = 10 + 偏移`。**正偏移完全正常**（不产生负时间戳），
所以这个 bug 只在"音频提前"这一半出现 —— 而那正是偏移功能最常用的方向
（配套素材说明里推荐的用法就是 `-3000` 配 `13_音频前3秒是静音`）。

同一个文件用 `-copyts` 回读还能看到容器内部已经自相矛盾：
`nb_frames` 说 470 帧（10 秒的量），音频包却只覆盖 `[-1.02, 6.98]`。

**修法**：预览改用音频滤镜表达同一个偏移 —— 负偏移 `atrim=start=|偏移|,asetpts=PTS-STARTPTS,apad`，
正偏移 `adelay=<毫秒>:all=1`。产物永远非负，实测与正式输出的对齐在预览窗口内逐拍一致，
音频恒为完整 10 秒。详见 ADR-022。

**第二条通路（同一症状）**：预览原本固定写 `preview.mp4`，播放器可能继续显示上一次
读进内存的内容，或者占着文件让 `File.Move` 抛异常 —— 用户看到的同样不是刚生成的那一份。
现在每次都是新文件名（ADR-023），并在生成前删掉上一次的。
预览弹窗还会写出"本次偏移 -3000 毫秒"（ADR-024），
这样"参数没进去"和"看的是上一次的文件"就能一眼分开。

## 五、设计决策（全部记录在 ADR.md，这里给索引）

`docs/ADR.md` 有 24 条，每条附实测依据。要点：

| # | 决策 | 一句话理由 |
|:--|:--|:--|
| 001 | 用 `-c copy` 封进 MKV | CRC 证明逐字节一致 |
| 002 | `-avoid_negative_ts disabled` 是强制项 | 否则负偏移静默推迟画面（4.2） |
| 003 | `-itsoffset` 位置有语义 | 写错不报错、只是失效（4.3） |
| 004 | 只有"物理上不可能"才拦住用户 | 用户最怕程序悄悄替他判断 |
| 005 | 位深取 `bits_per_sample` | `sample_fmt` 会把 24 位显示成 32 位（4.5） |
| 006 | 时长比对容差 0.1 / 0.5 秒 | 视频音频天然有帧对齐误差 |
| 007 | 先写 `.partial.mkv` 再改名 | 失败不留半成品 |
| 008 | 丢弃全部容器元数据 | 源容器的 duration 是按旧音轨写的 |
| 009 | 用 ffprobe 而非 `ffmpeg -i` | 结构化输出，升级不易坏 |
| 010 | 构建脚本 `.bat` 保持纯 ASCII | 见 8.1 |
| 011 | 绿色目录而非单文件 exe | 可替换 ffmpeg + 启动快 |
| 012 | 主界面只放核心动作 | 初版一屏塞了九件事 |
| 013 | 一条信息只在一个地方出现 | 初版同一句话说三遍 |
| 014 | 状态行没有内容时不占位 | 按钮含义自明，再挂一句是噪音 |
| 015 | 卡片内容垂直居中 | 比"用信息去填满"更能解决"太空" |
| 016 | 文字对比度 ≥ 4.5:1 | 实测旧值只有 3.4:1 和 2.4:1 |
| 017 | 偏移入口整块可点 + 同时显示秒 | 用户量到的是"0.3 秒"不是"300 毫秒" |
| 018 | 提醒用独立弹窗而非行内展开 | 行内展开会把按钮挤出窗口（6.3） |
| 019 | 界面尺寸反复出错的教训 | 别靠估算窗口高度；`DesiredSize` 会骗人 |
| 020 | 音频不限于线性 PCM | FLAC/ALAC/WavPack 也能 copy（4.4） |

| 022 | 预览的偏移用音频滤镜，不用 `-itsoffset` | mp4 存不了负时间戳，音频被静默砍短（4.8） |
| 023 | 预览每次都用新的文件名 | 播放器会继续显示上一次的预览，或占着文件让改名失败 |
| 024 | 预览状态里写出本次用的偏移 | "参数没进去"和"看的是上一次的文件"症状一模一样 |

### 关于"只提醒不拦截"

这是贯穿全工程的产品基调，值得单独说：

**按钮变灰的条件只有两个** —— 槽位为空，或文件里没有视频流/音频流。
外加唯一一个"确定做不到"的编码：裸 TrueHD。

时长不一致、体积过大、8 位位深、浮点 PCM、**有损编码**、源视频有多条音轨 ——
**全部只出提醒，按钮照常可点。**

理由：目标用户是音频制作者。他们最怕的不是报错，而是程序悄悄替他们做了判断；
反过来，因为差了 0.2 秒就不让干活同样不可接受。

推论：界面上不该有"验证通过/不通过"这种审判式状态，只平铺事实 + 在有风险处标琥珀色。

## 六、开发过程中踩过并修掉的坑

这一节记录**真实发生过的错误**，包括我自己写出来的 bug。留着是因为它们可能复发。

### 6.1 音频判据把两件事混成了一件（功能缺失）

**症状**：FLAC / ALAC 被拒绝，理由是"不是线性 PCM"。

**根因**：旧实现只认 `codec_name` 以 `pcm_` 开头。但判据应该是"能不能 copy 进 MKV"，
而 FLAC 同样能 copy、且搬完仍然无损。一个错误的判据同时产生了两种错误 ——
拦了该放的（FLAC），也没意识到该警示的（MP3）。

**为什么测试没发现**：当时只覆盖了"PCM 通过 / AAC 拦下"，没覆盖 FLAC。

**修法**：新增 `AudioCodecs` 类，把判据独立出来，并按实测清单分类（见 4.4）。

### 6.2 负偏移被静默"修正"（差点写进产品）

`CommandBuilder` 第一版没加 `-avoid_negative_ts disabled`。
是实测（4.2）才发现 ffmpeg 会把视频推后而不是报错。

### 6.3 "点详情没反应"（用户报的真实 bug）

**症状**：点主界面的「详情」按钮，按钮文案变成「收起」了，但展开的内容一个字看不到。

**根因**：提醒做成**行内展开**，展开后内容变高，把「开始」按钮和状态行
**推出了窗口下边界**。

**修法**：提醒改成独立弹窗（`NoticesDialog`）。主窗口高度恒定，
从根上不存在"点击后内容变高挤坏布局"这类问题。顺带把散在两个卡片里的提醒汇总成
一份带来源标注的清单。

### 6.4 测试"通过"了但根本没跑

**症状**：新增的 FLAC 端到端测试报告通过，但用时只有 **2 ms**。

**根因**：素材目录的向上查找写得不稳：

```csharp
// 错：
dir = Path.GetDirectoryName(dir.TrimEnd(Path.DirectorySeparatorChar));
```

分隔符有 `\` 和 `/` 两种，`TrimEnd` 容易漏掉一种，逐级向上时停在了错误层级。
于是 `SampleFilesTests` 里**所有**测试都静默 `return`（因为素材"不存在"），
而报告一直显示全部通过。

**修法**：改用 `Path.GetFullPath` 归一化后取父目录。
FLAC 测试从 2 ms 变成 242 ms。

**留下的防线**：新增 `EnvironmentTests`，显式断言 ffmpeg/ffprobe 找得到、能执行，
并有一条测试把"向上查找素材"的过程断言出来（找不到就失败并列出所有试过的路径）。

**教训**：**"测试通过"和"测试跑了"是两回事。** 带条件静默跳过的测试，
必须另有一条测试盯着那个条件。**判据是看用时** —— 端到端测试几毫秒完成本身就可疑。

### 6.5 按钮缩成 38px 的小方块

**症状**：主按钮实测 `Bounds = 0,16,38,50`（宽 38px），贴在左边。

**根因**：按钮放在 `RowDefinitions="Auto,Auto"` 且**没有声明列**的 Grid 里，
被按内容测量。

**修法**：显式声明 `ColumnDefinitions="*"` + `HorizontalAlignment="Stretch"`（修好后 836px）。

### 6.6 `SizeToContent="Height"` 与实际布局差 36px

**症状**：底部「开始」按钮和状态行被切在窗口外，底部漏出一条背景。

**实测**：`ClientSize = 880x560`，`Content.Desired = 404`，但 `Content.Bounds.Height = 368`。
`SizeToContent` 按 DesiredSize 定窗口高度，实际布局又给了不同的高度。

**更坑的是**：`SizeToContent` 在内容**动态变化后不重新测量** ——
实测三个不同状态的窗口高度都是 478，全是启动那一刻（空状态）测出来的。

**修法**：改用固定高度 + 自适应行（星号行伸缩）。

### 6.7 用 `DesiredSize` 判断"内容放得下"是错的

`Content.DesiredSize` 报 408 < 560，看起来没问题，但截图显示明显裁切。
因为 `DesiredSize` 是在**约束下**测量的，会返回约束后的值。
`SizeToContent` 栽在同一个坑上。

**可靠的做法是截图对照，不是读 `DesiredSize`。**

### 6.8 我自己写的无限递归

用全局替换把 `Raise(nameof(HintText))` 换成 `RaiseHint()`，
结果把 `RaiseHint()` **方法定义里的第一行**也换了，方法变成调用自己 → 启动即崩
（`0xC00000FD` 栈溢出）。

**教训**：全局文本替换要排除定义本身。

### 6.9 包装底部区域时把时长条盖掉了

为了给底部操作区加对齐内缩，我用字符串切片包装了一段 XAML，
结果 `Grid.Row="1"` 的时长条和新的底部区**行号撞车**，时长条被覆盖；
而且包进去的子元素还带着无效的 `Grid.Row` 属性。

**教训**：改 XAML 结构后要**读回来确认**，别只看构建有没有通过。

### 6.10 `-n` 导致 ffmpeg 静默不写文件（我自己测试时踩的）

做对比实验时用 `-n`（不覆盖）重复跑，ffmpeg **拒绝写入**已有文件，但我把它当成了新生成的结果。
证据是输出体积和上一次**完全相同**。

**教训**：脚本里重复生成时用 `-y`，或者先删旧文件；核对"体积变了没有"能识破这种情况。

### 6.11 SSIM 测不准，所以放弃了量化画质

想用 SSIM 量化"重新编码掉了多少画质"，但实测**连画面与源逐字节相同的那一版都拿不到 1.0**
（报了 0.983），说明测法不可靠（多半是帧对齐问题）。

**处理**：不在文档里给"画质下降了多少"这类分数，只给能自己复核的事实（CRC、码率、体积）。

**原则**：与其给一个可疑的数字，不如只给能复核的证据。

`build.ps1` 参数：`-SkipZip`（只出目录）、`-NoPause`（不等待按键，脚本/CI 用）。

### 压缩包为什么叫 `Windows.zip` 而不是 `替音工具.zip`

1. Release 资产名要和 README 里的下载链接一致（曾经对不上，每次发版要手动改名）
2. 中文资产名在 URL 里会被百分号转义

### ffmpeg 来源与许可

| 部分 | 许可 |
|:--|:--|
| 本仓库代码 | **MIT** |
| `bin\ffmpeg.exe` | **GPL v3** |

实测确认：该构建配置含 `--enable-gpl --enable-libx264 --enable-libx265`，
`ffmpeg -L` 输出 GPL v3 声明。

ffmpeg 是独立进程调用（`Process.Start`），没有链接其代码，两者许可分开。
**别人转载 zip 时 ffmpeg 的 GPL 义务跟着走**，README 和 LICENSE 里都注明了。

## 八、环境相关的坑（Windows / PowerShell）

这些坑与业务逻辑无关，但每次都能浪费半小时。

### 8.1 `.bat` 必须是纯 ASCII

`cmd.exe` 逐字节读 `.bat`，按 ANSI 代码页解释。
**GBK 下某些汉字的尾字节是 `0x5C`（反斜杠）**，会被当成续行符，
导致脚本从那里开始整体错位。

实测症状：`https:` 被吃成 `ttps:`，报出一堆 `'not' is not recognized`。

所以 `build.bat` 只有一行纯 ASCII 转发，逻辑全在 `build.ps1`。
验证：`[IO.File]::ReadAllBytes('build.bat')` 最大字节值应 ≤ 127。

### 8.2 `.ps1` 必须保存为 UTF-8 **带 BOM**

Windows PowerShell 5.1 在没有 BOM 时按 ANSI 代码页读 `.ps1`，中文全变乱码，
而报错信息**完全指不到真正原因**：

```
Unexpected token '鐢ㄩ€?' in expression or statement.
Missing closing ')' in statement block or type definition.
```

**这个坑踩过三次**（编辑器、格式化工具、自动化改写都可能悄悄去掉 BOM）。

**现在有防护**：`build.ps1` 启动时会自检并自动补上 BOM（实测有效）。
验证：`[IO.File]::ReadAllBytes('build.ps1')[0..2]` 应为 `EF BB BF`。

### 8.3 PowerShell 会把原生命令的 stderr 提升成异常

ffmpeg 的 banner 和进度都写 stderr。在 `$ErrorActionPreference='Stop'` 下：

- `2>&1 | Out-Null` —— **没用**
- `*> $null` —— **同样没用**

脚本会直接中断，报的还是 ffmpeg 的版本号（极具误导性）。

**解法**：用 `Start-Process` 把输出重定向到文件，彻底绕开这个机制。

### 8.4 形参不能叫 `$Args`

`$Args` 是 PowerShell 的自动变量（当前函数的参数数组）。
用了它，函数里拿到的永远是空值，报错是：

```
Cannot validate argument on parameter 'ArgumentList'.
```

所以 `build.ps1`/生成脚本里用的是 `$FfArgs`。

### 8.5 ffprobe 要用 `-v quiet` 而不是 `-v error`

否则损坏文件会让 ffprobe 往 stderr 写 `moov atom not found`，
触发 8.3 的同一个问题。

### 8.6 中文文件名在 git 里显示成转义

```
"docs/\344\275\277\347\224\250\350\257\264\346\230\216.md"
```

这是正常现象。想看中文：`git -c core.quotepath=false status`。

### 8.7 换行符

`.gitattributes` 已定死策略：源码与文档 LF，`.bat`/`.ps1` CRLF。
不设的话，这个工程（`.cs` 是 LF、`.bat`/`.ps1` 是 CRLF）每次检出都会产生
"整个文件都变了"的假 diff。

### 已知限制

- **只支持 Windows x64。**
- **一次只处理一个视频 + 一个音频。** 拖入多个时按类型各取第一个，并在状态栏说明忽略了几个。
- **只按 `0:v:0` 和 `1:a:0` 取流**，不提供流选择界面。
- **不做音频对齐分析**：只比对时长，不比对内容。偏移需要用户自己听、自己调。
  （测试素材 `13_音频前3秒是静音_工具查不出.wav` 就是专门演示这个边界的。）
- **不保留源视频的音轨**：输出里只有你给的那一条。想保留原曲伴奏要在 DAW 里自己混好。
- **绿色目录根层 200+ 个文件**（自包含发布的代价），用户只需要看 exe 和 `bin\`。
- **预览与正式输出的时间戳行为不同**：正式输出是 mkv 拷贝、用 `-itsoffset`（能带负时间戳）；
  预览是 mp4 重编码、用音频滤镜（`atrim` / `adelay`）表达同一个偏移（4.8）。
  两者在预览的 10 秒窗口内对齐完全一致。
- **预览文件每次都是新名字**，并且生成新的之前会删掉上一次的（4.8）。
  所以你没法把两次预览并排对比；需要对比请在正式输出上比。

## 十一、还没验证 / 下次可以做的

诚实列出没做完的部分：

### 未验证

1. **负偏移的成品在剪辑软件里的时间线对齐。**

2. **界面动效的实际手感。** 悬停抬起（1.006 倍）、进度条、拖拽高亮、启动淡入
   都只保证了参数合理（150–220ms），好不好看需要人来判断。

3. **`-progress pipe:1` 的 `out_time_us` 精度。** 目前只用于百分比显示，
   即使偏一点也只影响进度条观感，不影响产物。

4. **带 AC3 核心的 TrueHD 轨道**（`truehd_core`）能否 copy。
   只测了裸 TrueHD（失败）。这种组合流没测过。

- 让用户选择保留源音轨（目前丢弃）

- 界面多语言（目前只有中文）

## 十二、给接手者的三条建议

1. **改 `CommandBuilder` 前先读 `docs/ADR.md` 的 002 / 003。**
   那里两个参数删掉都不会报错，只会让用户的成品悄悄出错。有测试守着，但要知道为什么。

2. **改 XAML 后一定截图确认，别信 `DesiredSize`，也别只看构建通过。**
   这个工程的界面坑几乎全是"构建通过但渲染出来是坏的"（见 6.5–6.9）。

3. **改完 `.ps1` 后确认 BOM 还在。**
   这个坑累计踩了三次，每次的报错都指向完全无关的地方。
   现在 `build.ps1` 有自检，但那只在跑构建时生效。
