# 把封面视频换成你自己的音频，为什么可以不损失画质

如果你做过翻唱，多半遇到过这件事：

找到一支合适的 MV，想把自己的混音换上去。搜到的教程大概会说"用剪辑软件导出一下"、
"用格式工厂转一下"。照着做完，成品能播，但画面看着比原片糊了一点，
声音的细节也没了原来的味道。

这篇文章讲的是另一条路：**把视频流和音频流原样搬进一个新容器，一个字节都不重新编码。**
顺便解释为什么常见的做法必然会损失，以及什么时候这条路走不通。

不需要懂视频编码。你只需要懂音频——而这部分你本来就懂。

---

## 一、先看清楚：常见做法为什么会损失

视频文件由两部分组成：**画面** 和 **声音**。它们各自是独立的数据流。

"替换音频"这个动作，天然只涉及声音那部分。画面根本不需要动。
但绝大多数工具的工作方式是：

```
原视频 ──[解码画面]──[解码声音]──> 丢掉旧声音
                                      │
                                      ├── 混入你的音频
                                      │
        [重新编码画面] <──────────────┘
        [重新编码声音]
              │
              v
           输出文件
```

问题在于**"重新编码画面"这一步。** 它本来完全没必要发生。

视频编码不是无损的。原片的画面已经是压缩过一遍的结果，
你把它解码再压一遍，等于把一张 JPEG 再存成 JPEG —— 每次都会掉一点质量。
这个过程不可逆，而且**你看不出具体掉了什么，只会觉得"没原片那么清楚"**。

更麻烦的是，很多工具默认用的编码参数并不适合"只是换个声音"这个场景：
为了控制体积，它会给你一个更低码率的画面。

### 关键认识

**"换个声音"和"重做画面"是两件完全独立的事。**
常见工具把它们绑在一起，这才是损失的来源 —— 不是因为压缩本身有多可怕，
而是因为**根本不需要压**。

### 一组可以直接对比的数字

同一支 1080p / 8 Mbps 的素材，配同一个无损音频，两种做法：

| | 总体积 | 画面码率 | 输出里的音频 |
|:--|:--|:--|:--|
| **源素材** | 14.35 MB | 8022 kbps | — |
| **只换容器（本文方法）** | 18.48 MB | **8022 kbps（完全没变）** | pcm_s24le 2304 kbps |
| **重新编码（常见做法）** | 7.65 MB | **约 4270 kbps（掉了一半）** | aac |

三件事值得注意：

**1. "零重编码"的成品反而更大，这很正常。** 因为音频变成了未压缩的 PCM（2304 kbps）。
体积大不是缺点，它恰恰是"音频没被压过"的证明。

**2. 重新编码那一版，画面码率从 8022 掉到了约 4270 kbps。** 少掉的这一半，
就是被丢掉的画面信息。这个过程不可逆。

**3. 画面是否被动过，是可以客观验证的**，不需要靠眼睛判断 ——
对两条视频流各算一次校验和即可：

```
源素材的画面的校验和   0x984dd037
只换容器后的画面       0x984dd037   ← 完全一致，逐字节相同
重新编码后的画面       0x9096a4f1   ← 已经不一样了
```

这是"零损失"这个说法最硬的证据：不是"损失很小"，而是**数据完全没变**。

> 顺便说明：我没有给出"重编码后画质下降了多少"这类分数。
> 我试过用 SSIM 去量化，但实测发现连"画面与源逐字节相同"的那一版都拿不到满分（1.0），
> 说明测量方法本身不可靠 —— 那与其给一个可疑的数字，不如只给你能自己复核的事实。

## 二、正确做法：换容器，不碰内容

先介绍一个概念，理解它之后就全通了。

### 容器 ≠ 编码

一个 `.mp4` 文件其实是**一个盒子**（容器），里面装着几条**独立的流**：

```
video.mp4  (盒子 / 容器)
├── 流 1：画面   编码 h264
├── 流 2：声音   编码 aac
└── （可能还有字幕、章节、封面图）
```

- **容器**决定"盒子长什么样"（文件结构、能不能放章节、扩展名叫什么）
- **编码**决定"里面的东西怎么压缩的"

这两件事是**分开的**。

这个结构你其实很熟 —— 就像 DAW 的工程文件里装着若干条独立音轨，
每条轨可以是 WAV 也可以是别的，工程文件本身不决定音轨的格式。

**既然盒子是盒子、内容是内容，那"换个盒子"就不需要动内容。**

于是正确做法是：

```
原视频 ──> 取出【流 1：画面】──────────────┐
                                          ├──> 装进新盒子 ──> 输出文件
你的音频 ─> 取出【流 1：音频】─────────────┘
```

全程只做"搬运"和"重新打包"，**没有任何解码、没有任何编码**。

在 ffmpeg 里，这个动作叫 `-c copy`（`c` = codec，`copy` = 原样拷过去，
即"不要编码，直接搬"）。

### 为什么这样就没有损失

因为它压根没处理你的数据。画面数据是原封不动搬过去的，
音频数据也是原封不动搬过去的 —— 不是"损失很小"，是**字节级完全相同**。

这一点是可以验证的，不是修辞：对原视频的画面流和输出文件的画面流各算一次校验和，
两者应当完全一致。工具里有专门的测试守着这件事。

### 顺带的好处：快到不真实

不用解码、不用编码，意味着处理速度**只受硬盘速度限制**。
几分钟的视频通常十几秒就完成 —— 因为实际上只是在拷贝数据。

## 三、代价：你的音频必须是无损的

没有免费的午餐。`-c copy` 的意思是"原样搬"，所以它当然要求
**你的音频格式能被直接装进目标容器**。

这里是这件事唯一真正的约束，也是你作为音频制作者需要配合的唯一一步。

### 关键区分："能搬进去"和"本身无损"是两件事

先把这两个问题分开，后面的判断就都通了：

| 问题 | 决定什么 |
|:--|:--|
| 这个编码能不能**不重编码**地装进 MKV？ | 技术上做不做得成 |
| 这个编码**本身**有没有损失？ | 成品的声音有没有损失 |

两件事的答案可以不同：

- **FLAC** 能装进去，而且它本身无损 → 成品无损 ✓
- **MP3** 也能装进去，但它本身有损 → 成品有损 ⚠
- **TrueHD** 装不进去 → 做不成 ✗

所以"能用什么格式"的完整答案是：

**无损的（推荐）**：未压缩 PCM（WAV / CAF）、无损压缩（FLAC / ALAC / WavPack）。

**有损的也能用**：MP3 / AAC / Opus / Vorbis / AC3 都能原样搬进 MKV ——
只是搬进去之后仍然是有损的。工具会明确提醒你这一点。
它不是"经过工具就变无损了"，而是"原样保留它原来的样子"。

### 装不进去会怎样

这是真正的陷阱所在。假设某种编码容器不认：

**情况一：报错。** 至少你知道出问题了。这是好的情况。

**情况二：不报错，但自动帮你重新编码了。**

这第二种最危险。你要求"原样搬"，工具发现搬不了，
于是"帮你"编码成另一种有损格式装进去 —— 体积小了很多，画面正常，
**你不会收到任何提示**。

实测过一次：同一支视频配同一个无损音频，

| 写法 | 输出里的音频编码 | 体积 |
|:--|:--|:--|
| 原样搬运 | pcm_s24le（无损） | **8.49 MB** |
| 被自动编码 | vorbis（有损） | 0.46 MB |

差了 18 倍。**体积突然变得很小，就是"它在偷偷压你的音频"的信号。**
（这个差别太大了，其实也给了你一个很实用的自查手段。）

> 这也是为什么工具会**主动拦住** TrueHD —— 它是实测唯一装不进 MKV 的编码。
> 拦住不是刁难，是避免你拿到一个静默损失过的成品。

### 无损的三种选择

**线性 PCM / Linear PCM / 未压缩** —— 就是 WAV 里面装的那种东西，
每个采样点老老实实存着，没有任何压缩。

它的好处是**最通用**：任何容器都认识它，不存在"装不进去"的问题。

不过它体积最大（48 kHz/24 位/立体声 = 0.275 MB/秒）。所以还有两个更省地方的选择：

| 格式 | 性质 | 5 分钟约 |
|:--|:--|:--|
| **CAF**（PCM） | 未压缩，超长音频支持最稳 | 82 MB |
| **WAV**（PCM） | 未压缩，最通用 | 82 MB |
| **FLAC** | **无损压缩**，解开后与原始数据完全一致 | 约 40 MB |
| **ALAC** | 无损压缩，Apple 系常用 | 约 40 MB |

四个都是无损的，装进成品后声音完全一样。**选哪个看你方便**。

> FLAC 的"无损压缩"和你熟悉的概念一致：类似于 ZIP 之于原文件 ——
> 压过，但解开后一模一样。
>
> ⚠️ 早先版本的工具只认未压缩的 PCM，会把 FLAC 拒之门外，那是错的。
> 现在 FLAC / ALAC / WavPack 都直接支持。

### 在 DAW 里导出时选

| 设置项 | 选什么 |
|:--|:--|
| 格式 / 容器 | **CAF**（推荐）或 **WAV** |
| 编码 | **线性 PCM / Linear PCM / 未压缩** |
| 位深 | 16 位或 24 位 |
| 采样率 | 和源视频音轨一致最省事（不一致也能用，见下） |

**为什么推荐 CAF 而不是 WAV：** CAF 是 Apple 的容器，对超长音频和
超过 4 GB 的文件支持更稳。WAV 也完全可以，几分钟的歌根本到不了那个量级。

**不要导出** MP3 / AAC(M4A) / FLAC / ALAC。这里特别说明 **FLAC**：

> FLAC 是无损压缩，很多人会认为"无损就能直接用"。
> 但它是**压缩过的** —— 无损指的是"解开后和原始数据完全一样"，
> 不是"没压缩"。对 `-c copy` 来说它是压缩格式，同样装不进去。
>
> 这个区别和你熟悉的概念是一致的：FLAC 之于 WAV，就像 ZIP 之于原文件。
> 解开后一样，但传输时是压缩状态。

### 关于采样率和位深：不用担心

你可能会想"源视频里的音频是 44.1 kHz，我导出的是 48 kHz，会不会有问题？"

不会有问题。`-c copy` 只是搬运，**采样率和位深原样保留**，
装在同一个容器里的两条流采样率不同是完全合法的。

但如果成品听起来"对不上拍子"，那才可能是采样率带来的问题（涉及重采样）。
工具会主动提醒你两边的采样率不同，让你自己判断。

## 四、这个方法的边界

任何方法都有适用范围。说清楚边界比夸大适用范围更值得信任。

### 能做到的

- 换掉视频里的音频，**画面和声音都零损失**
- 处理速度只受硬盘限制
- 保留原视频的画面规格（分辨率、帧率、色彩全都不动）

### 做不到 / 需要你自己处理的

**1. 不会帮你保留源视频原来的声音。**

输出里只有你给的那一条音轨。源视频自带的伴奏、和声、音效**会被整条丢掉**，
不是混音、不是叠加。

如果你想保留原曲伴奏，**要自己在 DAW 里把它和你的声音混好再导出**。
（这是个很常见的要求，所以工具会在界面上明确告诉你这一点。）

**2. 只比对时长，不比对内容。**

工具会告诉你"音频比视频短 5 秒"，但它看不出**你的音频是不是从第 0 秒对齐的**。

极端情况：两段音频时长完全一样，一段从头就是对的，
另一段前面多了 3 秒静音 —— 工具都会说"时长一致"，而后者出来的成品整体晚了 3 秒。

**这件事只能靠耳朵。** 所以工具提供"预览前 10 秒"，让你先听一遍再决定。

**3. 不解决"裁过片段"的问题。**

如果你在 DAW 里裁过长度导致对不上，那不是"整体偏移"，
而是内容错位，偏移功能救不了。请重新导出完整长度。

**4. 源视频的编码必须能装进新容器。**

绝大多数情况没问题（H.264、H.265、AV1、VP9 这些都行）。
但如果源视频用了冷门编码导致装不进去，工具会明确报错，
**不会偷偷帮你转码** —— 那会违背这个方法的全部意义。

## 五、工具做了什么

上面的方法其实是一条 ffmpeg 命令：

```
ffmpeg -i 视频 -i 音频 ^
       -map 0:v:0 -map 1:a:0 ^
       -c copy ^
       -avoid_negative_ts disabled ^
       输出.mkv
```

既然你懂了原理，这条命令你大概也能看懂：`-map 0:v:0` 取第一个视频流的第一个视频流，
`-map 1:a:0` 取第二个输入的第一个音频流，`-c copy` 原样搬。

**这个工具的价值不在"会写这条命令"，而在"让你不用写、也不会写错"。**
具体是四件事：

### 1. 不用装 ffmpeg、不用打命令

对做音频的人来说，装命令行工具、配 PATH、拼参数，每一步都是门槛。
绿色目录解压双击就能用 —— 这不是"好不好用"的问题，是"能不能用"的问题。

### 2. 拦住"看起来成功但结果是错的"情况

这是最实在的一条。上面第三节说的"自动帮你重新编码"就是典型：

**你拖一个 MP3 进去，工具会拒绝并告诉你原因，而不是给你一个悄悄损失过的成品。**
拒绝不是刁难，是因为它知道 `-c copy` 对压缩格式意味着什么。

### 3. 挡住两个很隐蔽的 ffmpeg 行为

这两个都是实测出来的，都会**静默出错**（不报错、但结果是错的）：

**其一：负偏移会悄悄推迟画面。**

填了"音频提前 3 秒"，ffmpeg 的默认行为不是裁掉音频开头，
而是**把整个画面往后推 3 秒**。实测数据：

| 参数 | 视频起点 | 音频起点 |
|:--|:--|:--|
| 默认 | **3.000 秒** | 0.000 |
| 加上 `-avoid_negative_ts disabled` | 0.000 | **-3.000 秒** |

上面那种情况，你得到的是一个画面和原片整体错位的成品，而且没有任何报错。

（注：具体数值会随音频采样点数量略有小数，比如 -2.952 与 -3.000 都可能出现，
取决于时长估算。要紧的是**画面起点有没有被推后**。）

**其二：偏移参数的位置决定它生不生效。**

`-itsoffset` 只作用于**紧跟在它后面**的那个输入文件。
写到前面去了，不是报错，而是**参数被无视** —— 你以为设了 3 秒偏移，实际是 0。

### 4. 让你核对得动、看得懂

- 选框里直接显示音频的实际规格（`pcm_s24le · 48000Hz · 24bit · 立体声`），
  **你可以一眼确认 DAW 导出设置对不对** —— 这比任何"验证通过"的印章都有用
- 时长不一致时给黄字提醒，但**不阻止你**。因为"音频比视频短"有时是有意的
  （比如你想让结尾静音）
- 出错时给人话，不是把 ffmpeg 的英文报错甩给你

## 六、快速上手

1. **DAW 里导出**：CAF 或 WAV，线性 PCM，完整长度
2. **打开工具**：解压，双击 `替音工具.exe`（注意 `bin` 文件夹要和它同层）
3. **拖两个文件进去**：视频放左框，音频放右框
4. **核对一下**：音频规格是不是你以为的那个
5. **点开始**

如果时长对不上，先点「预览前 10 秒」听一遍，再决定要不要用「音频偏移」。

## 七、一句话总结

**换容器，不动内容。**

视频画面的数据从头到尾没有被解码过、没有被重新压缩过，
只是从一个盒子搬到了另一个盒子。这就是它没有损失的原因 ——
不是"损失极小"，而是**根本没有发生会损失的操作**。

代价是你的音频必须是未压缩的线性 PCM，
以及你需要自己负责"内容对齐"这件事（工具只能帮你比对时长）。

## 八、想自己动手复核？

这篇文章里的数字都是实测的，你可以自己复现。复核"画面有没有被动过"只需要一条命令：

```powershell
# 对源素材的画面流算校验和
ffmpeg -i 源素材.mp4 -map 0:v:0 -c copy -f crc -

# 对成品算一遍，两者应当完全一致
ffmpeg -i 成品.mkv -map 0:v:0 -c copy -f crc -
```

两条输出的 `CRC=0x........` 相同，就说明画面是逐字节搬过去的。

如果你用测试素材里的
`docs\生成测试素材.ps1` 生成过素材（默认在仓库旁边的 `测试素材\`），
那么 `测试素材\对比实验\` 目录下有一组现成的对照文件：

| 文件 | 说明 |
|:--|:--|
| `源_1080p高码率.mp4` | 1080p / 8 Mbps 的源素材 |
| `A_零重编码.mkv` | 只换容器。画面 CRC 与源**完全一致** |
| `B_重新编码.mkv` | 重新编码。画面 CRC 已改变、码率掉了一半 |

直接拿它们跑上面两条命令，或者对比体积，就能亲眼看到差别。

## 附：几个常被问到的问题**Q：输出为什么是 MKV？不能是 MP4 吗？**

先说清楚一件事：**技术上 ffmpeg 能把 PCM 音频装进 MP4**（实测可以，不报错）。
所以这不是"做不到"，而是"不保险"——问题出在别处：

- **播放器和平台的兼容性参差。** 带未压缩 PCM 的 MP4 不是常见组合，
  不同播放器、不同剪辑软件、不同视频平台对它的处理不一致，
  有的直接不认音频轨。MKV 对未压缩音频的支持要宽松得多。
- **省一种出错的可能。** 输出格式固定是刻意的设计：少一个选项，就少一类问题。
  对目标用户来说，"格式选错了导致成品打不开"是完全没必要承担的风险。

**Q：输出文件为什么比原视频大很多？**

因为音频变成了未压缩的 PCM。这恰恰是"没有重新编码"的证明。

算得清楚一点：48 kHz / 24 位 / 立体声的 PCM 是 **0.275 MB/秒**。
所以——

| 音频时长 | 未压缩 PCM 占用 |
|:--|:--|
| 3 分钟 | 约 49 MB |
| 4 分钟 | 约 66 MB |
| 5 分钟 | 约 82 MB |
| 10 分钟 | 约 165 MB |

（这是用真实导出文件校准过的：30 秒的 48k/24bit 立体声 CAF 实测 8.24 MB。）

作为对比，同样 5 分钟的 AAC 128 kbps 只有约 4.6 MB —— 差了约 18 倍。
**所以"输出比源视频大不少"是正常的。**

反过来说也成立：**如果输出体积和原视频差不多，那就要警惕音频是不是被压过了。**

**Q：画质真的一点没变？**

画面数据是逐字节搬运的，所以是的。
但请注意 —— 如果你后来把这个成品上传到视频平台，
平台的转码会重新编码，那是另一回事，和这个方法的"零损失"不冲突。

**Q：我能顺便把画面裁一下 / 改分辨率吗？**

不能。任何对画面的处理都意味着重新编码，那就回到常见做法的老路了。
这个工具刻意只做一件事。
